# 프로젝트 목록 텔레메트리 운영

이 기능은 **Grafana와 독립적**입니다. 홈페이지의 기존 프로젝트 행 안에서 미러 1·2를 비교합니다. API 및 표시 기준은 [telemetry-contract.md](telemetry-contract.md)에 정의되어 있습니다.

## 무엇을 측정하는가

- 상태 수집 및 홈페이지 집계: 각각 15초 주기. 브라우저는 화면이 보일 때 15초마다 같은 origin의 `/status/mirrors.json`을 요청합니다. 여러 수집 단계를 거치는 주기적 스냅샷이지 연속 스트리밍이나 지연 없는 관측은 아닙니다. 마지막 관측 시각을 함께 확인합니다.
- **동기화 완료:** 기록된 rsync 결과 또는 검증된 작업 완료 계약에 근거합니다. HTTP 200, 디렉터리 mtime, upstream의 lastsync, 단순 `End:` 문구로 성공을 만들지 않습니다. 완료는 작업의 결과이며 다운로드 파일 전체의 암호학적 무결성 보증이 아닙니다.
- **동기화 중:** 실제 해당 작업 프로세스/관측기 프로세스 식별에 근거합니다. 남아 있는 락 파일만으로 실행 중이라고 하지 않습니다.
- **동기화 실패:** 실제 종료값/오류 근거가 있는 작업 실패입니다. 수집 장애나 과거 데이터는 별도의 미확인·오래된 데이터 상태입니다.
- **용량:** 실제 저장 디렉터리에 대한 GNU du의 할당 바이트, 저장소 안의 hardlink 중복 제외. 실시간 수집 루프와 분리해 낮은 CPU·I/O 우선순위로 순차 측정하며, 완료 후 1시간 간격으로 다시 측정합니다. 동기화 중 변경될 수 있는 비원자적 측정이고 저장소 간 공유 inode를 고유 물리 공간으로 중복 제거한 파일시스템 총량이 아닙니다. 측정 시각을 보며, 실패하면 이전 값의 시각을 그대로 보존합니다.
- **동기화 송수신 속도:** 해당 작업에 귀속할 수 있는 활성 TCP 연결의 연속 표본이 있을 때만 제공하는 관측값입니다. 짧은 연결·프로세스 종료 등으로 표본이 없으면 미확인입니다. 호스트 NIC 총량을 프로젝트에 배분하거나 progress2의 파일 재구성량을 네트워크 바이트로 바꾸지 않습니다.
- **최근 60초 HTTP 제공량:** 종료된 origin HTTP 요청의 response body 바이트입니다. HTTPS가 앞단에서 종료될 수 있으므로 HTTP/HTTPS를 임의 분리하지 않습니다. 진행 중인 대형 다운로드의 매초 속도가 아닙니다.
- **최근 60초 rsync 제공량:** 프로젝트 module의 완료 파일 기록 `%b` 집계입니다. 프로토콜/TCP/IP 전체 트래픽이나 고유 외부 이용자 수치가 아니며 미러 간 복제도 포함될 수 있습니다.
- 관측 시작·회전 누락·읽기 오류 후 60초 전체 관측 구간이 확보되기 전에는 제공량을 0으로 채우지 않습니다.

기존 10개 프로젝트 행을 유지합니다. Gentoo는 Portage, Kali는 images, Artix는 ISO와 weekly ISO까지 묶으며, 전체 14개 저장소를 각각 측정합니다. 저장소별 상세가 있으므로 일부 작업의 실패/미확인이 다른 작업의 성공에 가려지지 않습니다.

## 구성 및 경계

미러 호스트:

- 코드: `/opt/keimirror-telemetry/`
- 신뢰된 고정 설정: `/etc/keimirror-telemetry/config.json`
- 관측 결과: `/var/lib/keimirror-telemetry/runs/<repository>/state.json`
- 용량 캐시: `/var/lib/keimirror-telemetry/sizes.json`
- 공개 스냅샷: `/var/lib/keimirror-telemetry/public/snapshot.json`
- 공개 GET/HEAD 경로: `/.well-known/keimirror-status.json`
- 새 전용 HTTP 로그: `/var/log/nginx/keimirror-telemetry.log`

홈페이지 호스트:

- 집계 코드: `/opt/keimirror-telemetry/aggregate.py`
- 비로그인 전용 계정: `keimirror-status`
- 공개 집계: `/var/lib/keimirror-telemetry/public/mirrors.json`
- 공개 GET/HEAD 경로: `/status/mirrors.json`

공개 JSON에는 고정 project/repository ID, 제한된 상태·수치·시각만 허용합니다. 관리 API 키, SSH 키, 명령행, 내부 주소/경로, 이용자 IP, 파일명 및 원문 로그는 공개하지 않습니다. 브라우저는 SSH·Termix·Grafana나 미러 관리 API를 호출하지 않습니다. 집계기는 두 고정 HTTPS 주소만 TLS 검증·응답 크기 제한·시간 제한·리다이렉트 거부 조건으로 읽습니다.

새 HTTP 로그는 기존 로그를 대체하지 않는 **http-context의 추가 access_log**입니다. 고정 프로젝트 이름, 시각, body bytes, request bytes, 응답 상태만 기록하며 IP/URI/query/UA/referrer를 기록하지 않습니다. 기존 `/var/log/nginx/*.log` rotation 정책의 적용 여부를 설치 전에 확인합니다. 기존 vhost의 IP/ASN/봇 제한과 보안 헤더는 보존합니다.

## 동기화 작업 관측

새 rsync/rsync-ssl shim은 설치된 `/bin/bash -p`를 사용해 Python 시작 전의 환경·무시된 시그널을 전달하고, 원래 `/usr/bin/` 실행 파일을 같은 인수·환경·입출력으로 실행하여 실제 결과를 관측합니다. 동적 파일 디스크립터를 사용하므로 기존 락 디스크립터를 덮어쓰지 않으며, 실제 전송은 호출자의 프로세스 그룹에 남습니다. Python 직접 호출은 시작 전의 시그널 상태를 복원할 수 없으므로 운영 동기화에는 반드시 제공된 shim을 사용합니다. 전송 옵션·원본·목적지·cron 시간·기존 락·SSH 키는 바꾸지 않습니다. 전역 PATH는 변경하지 않습니다. 관측 파일 쓰기가 실패해도 실제 전송 결과를 바꾸지 않습니다. 상태 파일이 남았다는 이유만으로 현재 실행 중이라고 판단하지 않습니다.

기존 스크립트의 **실행 파일 경로만** 검증된 adapter로 교체합니다. 원본 버전/패턴이 다르면 중단하고 확인해야 합니다. upstream ftpsync 본체는 변경하지 않고 기존의 단계별 로그 및 완료 trace를 사용합니다. Kali의 허용된 rsync code 24는 경고와 함께 구분합니다.

스케줄이 긴 작업은 새 관측기 설치 후 다음 자연 실행 전까지 과거 성공을 확정하지 못할 수 있습니다. 보기 좋은 완료 상태를 만들기 위해 동기화를 강제 실행하지 않습니다. 예전 비활성 `keimirror-agent.service`의 고정 성공값/깊이 제한 용량 추정 코드는 사용하거나 활성화하지 않습니다.

관측기는 Linux의 단일 스레드 독립 프로세스로 실행하는 인터페이스입니다. 다중 스레드 Python 애플리케이션에 삽입하는 용도로 지원하지 않습니다. 관측기 PID 하나에만 SIGKILL을 보내면 자식에게 전달할 수 없으므로 강제 종료가 필요할 때는 기존 작업의 프로세스 그룹/cgroup을 대상으로 합니다. 인터프리터 자체의 실제 동기적 결함(crash)도 복구 대상으로 지원하지 않습니다. 종료 결과가 기록되지 않은 작업은 완료가 아니라 미확인으로 처리합니다.

## 안전한 설치 순서

1. 배포할 Git 커밋을 고정하고 생성물 검사, 전체 Python·브라우저 검사, 독립 리뷰를 통과시킵니다. 운영 서버의 실제 vhost/root/원본 스크립트/hash/사용자/실행 파일을 다시 확인합니다.
2. 수정할 nginx 설정·동기화 스크립트·신규 경로의 사전 존재 여부, 기존 SSH 공개키 파일 hash 및 cron 내용을 비공개 증거로 보관합니다. 웹 루트 밖의 owner-only 백업을 만들고 해시와 아카이브 가독성을 검사합니다. 인증서 개인키나 미러 데이터셋을 복사할 필요는 없습니다.
3. root-owned 코드를 새 `/opt` 경로에 설치합니다. shim은 실행 가능하며 원래 바이너리가 그대로 존재해야 합니다. 설정은 자격증명을 포함하지 않는 root-owned 파일이고 기존 작업 사용자가 읽을 수 있어야 합니다. 각 `runs/<id>` 디렉터리는 해당 기존 작업 사용자만 쓰도록 준비합니다. collector의 private cursor와 공개 snapshot은 별개입니다.
4. adapter dry-run 및 원본 hash 조건을 확인합니다. 모든 수정본의 shell syntax를 확인한 뒤 원자적으로 교체하고 원본 권한/소유자를 보존합니다. `--version` 등 비전송 명령은 원본과 동일한 결과여야 하며 동기화 상태를 새로 기록하지 않습니다.
5. nginx snippet을 정확한 vhost에 포함하고 `nginx -t`를 통과시킨 다음 graceful reload합니다. 기존 master 유지·포트·접근 규칙·디렉터리 제공을 확인합니다. 새 공개 경로는 정제 JSON 파일만 GET/HEAD로 제공합니다. 외부 포트나 관리 endpoint를 열지 않습니다.
6. 미러에는 `keimirror-status-collector.timer`, `keimirror-status-sizes.timer`, 홈페이지에는 `keimirror-status-aggregate.timer`를 설치·활성화합니다. 일회성 작업의 성공과 timer 활성화/부팅 연결은 각각 확인합니다. collector는 기존 `/tmp` 락을 볼 수 있어야 하므로 PrivateTmp로 숨기지 않습니다. 소켓 표본이 필요하므로 host network namespace를 유지하되 외부 네트워크 소켓 생성은 허용하지 않습니다.
7. collector의 제한된 private 상태와 공개 JSON을 읽어 값의 출처를 확인합니다. 초기 용량 측정을 낮은 우선순위로 완료하고 측정 중에는 미집계로 둡니다. 60초 관측 이후 완료 HTTP/rsync 제공량을 작은 실제 파일 요청으로 검증합니다. 전체 미러 다운로드나 인위적인 실패/대량 동기화를 실행하지 않습니다.
8. 홈페이지 호스트에 전용 비로그인 계정을 만들고 집계기를 실행합니다. 실제 미러 JSON의 schema·시각·ID를 검증하고 same-origin endpoint를 읽습니다. runtime JSON은 정적 웹 루트 밖에 있으므로 정적 rsync 배포로 삭제/덮어쓰지 않습니다.
9. 같은 검증 커밋의 프런트엔드를 배포합니다. 기존 GitHub SSH 자동 업로드가 실패하면 실행 종료를 확인한 후 승인된 기존 관리 연결로만 대체하며 키/접근 제어를 약화하지 않습니다. 코드/ops/테스트/문서는 정적 웹 업로드에서 제외합니다.
10. 운영 파일 해시·공개 응답·갱신되는 두 서버의 시각·10개 행/20개 미러 칸·상세 저장소·모바일/한영/테마/오프라인·미확인 표시를 확인합니다. GitHub에 같은 소스와 배포 결과를 남기고 임시 스테이징/테스트 서버만 정리합니다.

## 롤백 및 제한

- 기능 롤백은 새 timer 정지, 원래 스크립트 및 nginx 설정 복원, `nginx -t` 후 reload, 이전 검증 프런트엔드 복원 순서입니다. 미러 파일/기존 동기화 일정/SSH 키는 롤백 대상으로 삭제하지 않습니다.
- 새 수집기 장애가 원래 동기화를 중단시키면 안 됩니다. 공개 파일은 원자 교체하며, 수집 실패 시 과거 스냅샷의 관측 시각을 바꾸지 않습니다. 홈페이지는 60초를 넘긴 자료, 미래 시각, 최신 가져오기 실패를 live 성공으로 표시하지 않습니다.
- timer 활성화는 실제 재부팅 시험과 동일하지 않습니다. 이 기능만을 위해 서버를 재부팅하지 않습니다.
- 백엔드 설치는 일반 정적 홈페이지 upload job과 분리된 관리 작업입니다. 정적 배포 workflow는 `telemetry/`, `ops/`, 개발 도구·테스트·문서를 제외합니다. 이후 백엔드 변경도 코드 리뷰·시험·고정 커밋·설치 hash 확인을 거쳐 별도 적용해야 합니다.
